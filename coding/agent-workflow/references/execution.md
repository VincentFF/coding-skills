# 执行与质量门禁

## 首次交接

主 agent 为每个新 worker 提供可独立执行的短交接：

- 目标、repo/cwd/ref、批准的任务及写入边界。
- 计划路径、相关 Spec/Design/ADR、必须遵守的约束和非目标。
- 验收条件、对应检查、期望证明的边界、最终集成义务。
- 文档或配置任务依赖的关键事实来源：路径和定位锚点；只列影响正确性的事实。
- 输出形式、任务状态写入者、允许的操作，以及需要请求主 agent 决定的条件。

原始契约是权威；交接摘要是阅读索引。worker 阅读相关原文，不把主 agent 的缩写当作完整要求。只发送当前任务需要的上下文，不复制整个计划、历史聊天或完整日志。

同一 worker 续跑只发送新任务、发现、变化的文件、证据路径和下一检查。更换 worker 时给首次交接和最近 checkpoint，并要求其验证当前工作树及所有权后再写入。

## worker 行为切片

1. **red**：新增行为先写并运行对应测试，确认失败指向缺失的行为。fixture、环境或测试编写错误先修复，不能作为 red 证据。已有有效复现测试时使用它，不重复制造失败。
2. **green**：在批准的边界内实现，直到对应完整检查通过。保留行为的回归测试可持续为 green，但必须说明它能捕获什么回归。
3. **record**：交付和检查均完成后才勾选任务，报告检查命令、关键结果、所证明的行为和剩余不确定性。red 适用时记录真实先后顺序，不把实现后的失败追认成实现前证据。

文档、配置和包装任务不强制 red。证据可以是机械检查，也可以是关键事实到权威来源的短映射；其中规范列表和标识符需要足够精确的路径/符号或行定位。无需为每句普通描述建立事实表。

任务勾选不是验收。默认 worker 更新其 Change 任务；并行组件只返回状态，集成写入者在交接集成并完成验证后更新权威台账，避免各 lane 产生互相冲突的完成状态。计划来源规定不同所有者时服从该约定。

在可验证的行为或集成边界留下 checkpoint：完成/未完成任务、精确检查及结果、当前文件和下一步。详细日志保存在运行产物中，checkpoint 用指针引用。

## 并行与集成

需要组件 lane、隔离 worktree 或跨仓库时，读取 `pi-subagents` 的 multi-lane orchestration 参考并遵守其 preflight、lane board 和交接要求。

任务切片决定交付内容；写入所有权决定能否并行。共享契约先确定所有者；依赖任务在前置交接可用后才启动。各组件留下 commit 或其他可恢复的持久交接，再由集成所有者处理跨组件连接和整体验证。主 agent 不在 worker 仍持有 worktree 时并发修补代码。

lane board 和插件运行状态用于所有权、run id 和恢复；Change 或项目任务系统仍是交付进度的权威。基础设施失败时保留现场，避免另起一个未知重叠的写入者。

## 审查前筛查

主 agent 先检查任务缺口、遗漏文件、已知失败和证据是否属于当前候选树。客观缺陷直接回到写入者；必要时跑聚焦检查。已有足够的当前树证据时，不为了筛查重跑昂贵全套测试。

独立 reviewer 的交接包含相关原始契约、完整变更文件清单及新增未跟踪文件、基准 ref、当前 diff/新文件的读取方法、worker 证据路径和最高风险边界。已提交的变更也属于审查范围，不能只看空的 working-tree diff。

## reviewer 检查

首次审查使用 fresh context，明确禁止修改项目文件；允许通过回复或插件管理的产物返回发现。只读审查期间保持候选源代码树稳定；会写生成文件的检查应由写入者执行或使用隔离位置。

分别给出两个方面的结果：

| 方面 | 检查内容 |
| --- | --- |
| 契约 | 所有重要验收条件、非目标和既有硬约束；必要文档同步；错误、兼容性、持久化和外部交互；检查是否真的证明承诺边界 |
| 项目标准 | 项目明确约定，以及影响可维护性的具体问题；工具已经强制检查的风格不再重复审查 |

检查测试是否会在目标行为被破坏时失败，是否实际被 runner 执行，是否存在跳过、吞掉断言或只检查内部实现的问题。unit fake 不能单独证明真实进程、存储或网络保证。核对 red 的失败原因和时间顺序；没有可审计的 red 时报告证据缺口，不虚构。

每项发现给出具体要求或标准来源、相关代码位置、违约或回归行为和证据。普通代码质量判断可说明为判断，不伪装成项目硬规定；没有契约、复现或源代码支持的猜测不阻塞。

## 发现处置与复审

| 类型 | 处置 |
| --- | --- |
| 契约阻塞 | 要求冲突、含义不明或需要新产品决定；主 agent 请求用户决定，先更新计划 |
| 实现缺陷 | 违反确定要求、源代码证实的回归，或必需保证缺少承诺边界证据；回到同一写入者修复和验证 |
| 可选建议 | 不改变契约且不影响验收；主 agent 接受或延后，不强制增加审查轮次 |

主 agent 先核实发现是否仍存在于当前树；已修复、被证据否定或超出范围的发现说明依据。初次 reviewer 尽量保留会话，复审只发送发现、修改范围和新检查；重大范围或契约变动后重新审查受影响的原始要求。

同一争议经过两轮仍无法解决时，将双方依据交用户裁决。带建议的通过结论不能包含未解决的契约阻塞或实现缺陷。

## 最终证据

最终检查在集成和最后一次相关修复后执行，绑定当前候选树。主 agent 独立运行必需机械检查，保存命令、结果和运行产物指针；之后发生修改时重跑受影响的检查，并请求必要的针对性复审。

区分已实现、经过行为测试、在承诺边界验证三种结论。环境、权限或依赖问题导致必需检查无法完成时，报告具体失败、已验证范围和恢复条件；不能把环境阻塞写成通过。
