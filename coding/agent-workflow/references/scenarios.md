# 场景走查

维护 skill 或首次试运行时使用。规则和路径检查只能证明文档约定完整、可读取；不能替代真实子 agent 的执行观察。试运行还要核对所读规则、red/green、独立审查及最终树证据。

| 场景 | 期望行为 |
| --- | --- |
| 用户只讨论方案或请 AI 编写 skill | 不因此启动委派或实施项目变更；写文件需要对应明确请求 |
| 普通措辞修正未进入 agent-workflow | 可用直接修改和聚焦检查，不制造 Change 或团队 |
| 显式进入 agent-workflow 的小变更 | 仍有独立 reviewer；非行为任务不制造 red |
| 一个登录目标包含多个任务 | 一份 Change，任务内嵌；不因任务多拆成多份 Change |
| 同轮讨论登录和权限两个交付目标 | 先确认各自验收与依赖，再生成多份 Change；不重复共享契约 |
| 旧项目没有长期文档 | 只补当前区域的最小 Spec/Design 基线，待交付目标留在 Change |
| Change 标为 approved 但无真实批准依据 | 核实来源，不能凭状态推断实施、委派或发布授权 |
| tdd/code-review 或所需原始契约不可读取 | 主 agent 预检或 child 加载阶段停止，不按摘要继续 |
| Spec 没说重复请求如何影响数据 | 属于影响数据语义的契约空白，先补契约；私有函数命名无需审批 |
| red 来自坏 fixture 或环境 | 不记录为行为 red，修复测试条件并确认真实症状 |
| fake 测试通过但承诺真实进程持久性 | 不宣称承诺已验证，补相应边界证据或报告阻塞 |
| worker 已提交代码，working-tree diff 为空 | reviewer 仍检查基准至候选的提交，并检查当前未跟踪新增文件 |
| 尚未同步的长期文档明确属于主 agent 收尾 | reviewer 对本轮候选给结论并列收尾义务；最终 accepted 前必须同步 |
| 本轮 writer 应交付的 README 缺失 | 按实现缺陷处理，不能当作主 agent 收尾义务跳过 |
| 同步只忠实合入批准差异 | 主 agent 检查一致性和受影响机械检查，不重新审批同一产品决定 |
| 同步引入新的行为或结构含义 | 重新批准并复审，不能通过改 Spec 掩盖缺陷 |
| 完整检查通过后又改了实现 | 原相关证据失效，重跑必要检查和受影响复审 |
| 两个 Change 都修改同一长期 Design | 主 agent 串行同步，并核对后续假设，不覆盖写入 |
| 必需验证或人工审批没有完成 | 保持未验收，说明阻塞；可选建议可以延后 |
| 最后只回写 accepted 状态或证据指针 | 重跑受影响文档检查；失败保持 approved，不重跑无关全套 |

真实试运行选择一个有明确公开行为、可重复测试和可控依赖的小变更。先观察最小闭环，再评估多 Change 或并行。没有指定试运行项目时不擅自修改其他仓库。
