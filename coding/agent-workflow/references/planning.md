# 规划与文档

## 文档职责

优先沿用项目现有位置和结构。没有约定时，使用以下位置；目录和文件按需创建。

| 文档 | 内容 | 默认位置与创建条件 |
| --- | --- | --- |
| Spec | 当前对外行为、约束和重要场景 | `docs/specs/<capability>.md`；需要跨变更复用的能力契约 |
| Design | 当前接口、所有权、数据流和失败处理 | `docs/design/<area>.md`；结构复杂或需要长期解释 |
| ADR | 关键决定、理由和有价值的替代方案 | `docs/adr/<number>-<decision>.md`；存在需要记住的取舍 |
| Change | 本次行为差异、必要设计变化、任务和验收方法 | `docs/changes/<change>.md`；非平凡变更的执行入口 |
| Glossary | 项目特有概念及规范用语 | `GLOSSARY.md`；已有术语歧义或新概念需要统一时 |

Spec 和 Design 描述当前系统，不按每次变更复制一套。Change 只写本次差异和相关长期文档指针。任务在 Change 中维护一份台账；已有 issue/task 系统是项目权威时，引用它，不再复制状态。

常规修复若已有契约足够明确，不新建长期 Spec 或 Design。复杂功能若需要持续使用的行为契约或结构说明，把创建或更新长期文档列入任务；减少文件不能省略必要契约。

## 权威与冲突

- 适用项目指令、现行 Spec 和 ADR 是基线。只读取受本次变更影响的部分，避免加载全部历史。
- 用户批准的 Change 差异只在明确列出的范围内代表目标行为；未提到的既有契约继续有效。
- 违反现行 ADR 的方案必须明确提出重开该决定，由用户批准，并在必要时新增替代 ADR。不要悄悄覆盖原决定的理由。
- 代码用于确认当前实现和影响范围，不自动否定已批准的目标契约。发现文档、代码或检查冲突时引用相关位置，请用户解决。
- accepted Change 是历史，不能覆盖后续现行 Spec、Design 或 ADR。

## 从讨论形成计划

1. 查看相关代码、测试、项目约定和现行契约。记录关键来源指针；代码能回答的问题不再问用户。
2. 澄清用户目标、非目标、可观察行为和失败场景。只有不确定且影响交付的事项需要询问，避免为填模板扩充 user stories。
3. 选择已有验证边界，写出验收条件及其失败模式。涉及真实进程、持久化或外部交互的保证，需要在对应边界验证；附近的 unit fake 只能证明它实际覆盖的部分。
4. 按完整可验证的行为拆任务，并标出真实依赖。大范围机械重构可按 expand–migrate–contract 分批；无法独立保持通过时明确最终集成检查，不假装每批独立可验收。
5. 补必要接口、所有权、错误处理、迁移或回滚设计。易从代码查到的文件清单和配置值优先用指针；不可见的限制和取舍才写入正文。
6. 检查每项重要验收条件被任务和验证覆盖，包括长期文档更新。无未决冲突后请求实施批准；仅用户真实批准后记录 approved。

任务需要可定位的目标模块或契约。长期文档用稳定概念和接口描述；worker 交接可提供具体路径、符号和编辑边界。不要把两者都限制成没有代码定位信息的泛泛描述。

## Change 模板

保留有实际内容的部分，删除不适用的可选部分。状态由主 agent 依据真实批准或验收更新，只有 `draft`、`approved`、`accepted` 三种。

````markdown
# <变更名称>

状态：draft

## 目标与范围

<用户问题、交付目标、非目标>

## 行为差异与验收

- AC1：<原行为 → 目标行为；重要场景及预期结果>
- AC2：<失败或兼容性场景及预期结果>

## 设计变化

<仅记录必要的接口、所有权、数据流、迁移或失败处理变化；引用相关 ADR>

## 任务

- [ ] T1：<完整可验证的交付>；验收 AC1；依赖无；目标 <模块/契约>；验证 V1。
- [ ] T2：<下一交付或必要文档更新>；验收 <条件>；依赖 T1；目标 <模块/文档>；验证 V2。

## 验证

V1：<检查的行为、会暴露的违约、实际证明的边界>

```bash
<完整可执行的验证命令>
```

V2：<下一检查或文档事实核对方法；来源路径/符号>

最终检查：<项目要求的机械检查及完整命令；只出现一次，任务可引用它>

## 相关长期文档

<相关 Spec、Design、ADR 和必要事实来源的路径；需要更新的位置>
````

行为验收条件、任务和验证可用 AC/T/V 标识互相引用，不在多个章节重复全文。命令来自项目实际脚本和测试入口；不要填写未经确认的占位命令后宣称计划就绪。

聊天计划也需要目标、非目标、可观察行为、目标模块和验证方法，不要求套用上述文件模板。

## ADR 与术语

只有以下三点同时成立才默认新增 ADR，项目另有强制要求时服从项目规则：决定难以逆转；没有背景会让未来读者困惑；确实比较过合理替代方案。

ADR 最小正文是标题加一段背景、决定和理由。仅在值得记住时补替代方案、非显然后果或替代关系。编号沿用现有规则；新目录使用递增编号。被替代的 ADR 保留原理由并指向新决定。

Glossary 只收项目特有概念，简短定义并统一名称；不存实现方案、任务或一般编程术语。没有术语歧义就不创建。

## 收尾与同步

- 将已批准且实际完成的行为差异同步到受影响的长期 Spec，结构变化同步到 Design，重要决定同步到 ADR。只修改相关部分，保留现有结构。
- 按修改后的文档核对实现、测试和来源。规范枚举、标识符、版本等事实核对权威代码或配置；文档不能把尚未完成的行为写成当前能力。
- 长期文档更新包含在最终候选 diff 中，接受同一轮相关审查和检查。没有需更新的长期契约时，说明原因即可，不为了收尾创建空文档。
- Change 保留为简短变更记录；不自动建立新的归档副本。后续 agent 只读取与本次任务相关的历史。
