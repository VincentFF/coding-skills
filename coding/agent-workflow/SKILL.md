# Agent Workflow

默认用一份 Change 文档连接规划、实施和验收。主 agent 保留用户沟通、需求决策、调度和最终验收权。

## 入口与授权

先确定本次请求的范围：讨论、规划，或执行已批准的变更。

- **讨论**：直接分析，不写文件、不启动 subagent。
- **规划**：用户请求生成计划时，可以写规划文档；这不授权实施。
- **执行**：先确认计划已获用户批准。用户明确要求执行现有且一致的已批准计划时，不重复索要批准。
- **委派**：用户明确要求通过 agent-workflow 执行、明确请求多 agent，或适用项目指令要求委派时，才使用 subagent。仅讨论、编写或评估本 skill 不构成委派授权；任务复杂度和风险也不构成授权。没有委派授权时直接执行，或说明收益后请求授权。

按本次请求或项目约定选择计划来源：默认轻量 Change；只有明确选择 OpenSpec 时，先读 [OpenSpec 接入](references/openspec.md)。存在 `openspec/` 目录不自动切换流程。项目既有文档和验收义务继续生效。

获得委派授权后、启动 subagent 前读取 `pi-subagents` skill，按所选分支加载它要求的参考文件；启动、续跑、隔离和异步控制以当前安装的插件指引为准。缺少插件或所需工具时报告接入阻塞，不自动安装或静默改用其他执行方式。

## 1. 规划

轻量入口在创建或修订计划前读取 [规划与文档](references/planning.md)。先查现有代码和相关契约，只向用户询问代码无法回答的目标、取舍和范围。

轻量入口的非平凡变更默认只新增一份 Change，包含行为差异、必要设计、任务和验证方法。已有计划足够明确时直接使用，不再生成同义文档。纯措辞修改、局部机械修改可使用用户批准的聊天计划；跨会话或需要团队交接时才持久化。

**就绪条件**：每项重要验收条件都有能在承诺边界暴露违约的检查；任务覆盖全部交付物和必要文档更新；要求与检查没有冲突；待决的产品或契约问题已由用户解决。完成模板或 CLI 校验不等于语义就绪。

## 2. 批准与分工

计划尚未获批准时，向用户呈现范围、关键契约或取舍、任务和验收方法，取得实施批准。影响已批准行为、兼容性或范围的新决定必须先回到计划，再恢复实施。

委派实质性实施前，按 `pi-subagents` 的 topology preflight 判断：单一紧耦合边界（single-seam），或多个独立可测试边界（multi-seam）。前者通常由一个 worker 完成；后者按插件要求划分隔离的组件所有者和后续集成所有者。业务任务没有依赖，不代表写入文件不会冲突。lane board 属于调度状态，不另建项目任务台账。

默认省略 scout；只有缺少影响范围或依赖证据且委派已授权时，才派一个有明确交付物的只读 scout。默认一个独立 reviewer；只有风险角度确实独立时才拆审查。

## 3. 实施

进入实施或审查前读取 [执行与质量门禁](references/execution.md)，并给各角色指向其任务相关的规则和原始契约。

每个 cwd/worktree 同时只有一个写入者；同一 lane 尽量保留同一个 worker 会话。交接以相关文件、验收条件和证据路径为主，续跑只发送变化。需要审批的决定由主 agent 路由给用户。

worker 逐个完成可验证的行为切片，运行对应检查后才勾选任务。新增行为使用有效的 red/green；保留行为说明回归检查；文档和配置用机械检查或权威来源核对。日志、checkpoint 和审查报告使用插件管理的运行产物，不默认写成项目文档。

## 4. 独立审查与修复

委派执行的候选结果必须经过首次 fresh-context、只读的 reviewer。直接执行路径由主 agent 审查；项目要求独立审查时，先取得委派授权。

reviewer 直接读取相关原始契约和当前代码树，分别报告契约符合性与项目标准问题，优先检查行为、兼容性、安全、持久化和承诺的验证边界。需求冲突交用户决策；实现缺陷回到同一写入者；可选风格建议不阻塞验收。修复后只复审受影响的范围。

## 5. 同步文档与最终验收

轻量入口按 [规划与文档](references/planning.md) 同步长期 spec/design 和必要 ADR；OpenSpec 入口遵守其接入规则。文档更新属于候选 diff，应在最终审查和验证前完成。

主 agent 在最后一次相关修改后，独立运行项目要求的最终机械检查；项目要求全套测试时运行全套。reviewer 的通过、任务勾选和 commit 都不能代替最终代码树验证。新增修改使受影响的检查和审查结果失效。

**验收条件**：所有必需任务及文档更新完成；必要审查通过；无未解决的契约冲突或实现缺陷；承诺边界和最终代码树的必需检查通过。必需验证无法运行时报告阻塞，不称为已验收。

交付只列结果、验证、剩余可选建议和运行产物路径。可引用现有耗时、tokens/cost 和审查发现来比较流程收益，不新增必填统计报告。轻量入口只有验收完成后才将 Change 标为 accepted；accepted Change 是历史记录，后续工作读取当前长期契约。

## 暂停与权限

- 需求矛盾、未批准的取舍或超范围工作：说明具体冲突，先更新计划并取得用户决定。
- 同一失败经过两次真实修复仍无新证据，或调试长期没有可检验的新假设：checkpoint 当前失败、尝试、已改文件和下一假设，由主 agent 决定继续还是升级。
- subagent 启动、工具或隔离失败：保留 run/worktree 和部分 diff，报告基础设施阻塞；未经用户批准不静默切换执行方式。
- 本地提交遵守适用项目策略；push、PR、发布、自动归档和破坏性清理需要各自明确授权。清理前确认无活跃所有者且交接已持久化。
