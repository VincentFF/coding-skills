# Codebase Design

用小而清晰的接口封装有用行为，让知识、变化和验证集中。优先项目已有领域语言和结构约束，不把参考词汇变成强制重命名规则。

## 共同词汇

| 概念 | 含义 |
| --- | --- |
| Module | 有接口和实现的职责封装，可以是函数、包或完整行为单元，不等于每个文件 |
| Interface | 调用者必须知道的完整契约：输入输出、约束、顺序、错误、配置和重要性能性质，不只有类型签名 |
| Implementation | 接口背后的内部结构 |
| Seam | 可替换行为或进行验证的位置；在当前计划中说明具体测试接口，避免术语歧义 |
| Adapter | 在该位置满足接口的一种具体实现 |
| Depth | 调用者学会少量接口后能够获得的行为能力，不按实现代码行数衡量 |
| Locality | 相关变化、问题和验证集中在明确职责中 |

## 形成设计共识

1. 读相关现行 Design、ADR、代码与调用者，明确本次要改变的职责和仍须保留的约束。只看受影响区域，不默认进行全仓架构审计。
2. 指明模块负责什么、不负责什么，谁拥有数据和状态；标出允许和禁止的依赖。为机械依赖约束选择可用静态检查，职责合理性保留给独立审查。
3. 描述关键接口及错误、顺序和副作用。选择能观察完整目标行为的已有接口进行测试；不要为测试公开私有状态或发明大量抽象。
4. 记录必要的关键交互和失败处理。输入输出、状态机或类型片段比文字更准确时可使用短片段，不复制工作演示或完整文件树。
5. 提出设计差异和取舍，交用户确认重要边界；不提前批准每个私有函数。worker 阅读本参考不获得重划批准模块或共享接口的权限。

## 结构判断

- 接口尽量让调用者少知道内部细节，完整行为由模块承担，不把协调复杂度散给所有调用者。
- 删除一个包装层时，复杂度若消失说明它可能只是转发；若散落到调用者，说明它承担真实封装。不要按模式名称自动删除。
- 只有真实变体、必要隔离或明确边界约束时增加抽象。生产和测试 adapter 可以构成真实需要，不为假想未来增加端口。
- 系统边界注入依赖，避免业务内部构造不可替换的客户端。纯计算尽量返回结果，必要副作用集中在明确的所有者。

涉及依赖隔离或合并浅模块时读取 [依赖与测试](references/dependencies.md)。用户需要比较明显不同的接口方案时读取 [方案比较](references/alternatives.md)；不默认启动多个 agent。
