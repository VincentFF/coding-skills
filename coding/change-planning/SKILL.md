# Change Planning

主 agent 将已有讨论整理成契约，不启动实施。用户只请求讨论时只分析；明确请求生成或修订文档时才写文件。

开始前读取 [文档契约](references/document-contract.md)。文档职责、Change 结构、状态和同步规则以该文件为唯一来源。

## 1. 提取共识与来源

读取相关代码、测试、项目规则、现行契约及人工审核材料。记录已确认决定、被否决方案、未决事项和需要调查的事实，保留原始来源指针。材料已读且没有变化时复用理解，不重复全仓扫描。

代码和环境事实由主 agent 查询；只向用户询问代码无法回答的目标和取舍。现行材料与代码不一致时先辨明有效决定，不把当前实现自动当作目标契约。

只读现有 Glossary 不需要加载领域建模规则。出现术语冲突或重要决定时读取 [domain-modeling](../domain-modeling/SKILL.md)；需要深入澄清时读取 [grilling](../grilling/SKILL.md)。已有共识不重新采访。事实调查默认直接执行；复杂度本身不授权委派。

## 2. 拆分交付目标

按可验收的交付目标提出一份或多份 Change；按完成目标的工作拆任务。一个目标有多个任务、worker 或会话，不自动拆成多个 Change。多个目标可以各有 Change，允许相互依赖，不要求单独部署。

向用户展示每份 Change 的名称、交付目标、验收方法和真实依赖，确认粒度后再生成正文。已有讨论已明确这些内容时不重复审批拆分。

任务优先是窄而完整的行为切片，可在相应接口验证；不机械按数据库、API、界面分成独立 Change。大范围重构按 expand–migrate–contract 分阶段迁移；阶段不能独立验证时，明确最终集成验收。共享目标契约只记录在一个所有者 Change，其他 Change 引用它。

## 3. 补设计与验证

重要模块、接口、所有权或依赖变化先读取 [codebase-design](../codebase-design/SKILL.md)。提出必要结构约束，不预先批准每个私有函数或局部算法。迁移、回滚、兼容性及失败处理只在影响交付时展开。

选择已有且能观察目标行为的测试接口，说明检查会捕获什么、证明到哪一层。涉及真实进程、存储或网络的保证，需要相应边界证据；fake 不能替代该保证。确认必要的测试接口和验证范围，后续 TDD 不逐个测试重复询问。

保留所有重要验收场景，不为凑模板扩充 user stories。验证命令来自实际脚本和 runner；无法确定必需验证入口或条件时明确阻塞，不填写占位命令后宣称就绪。

## 4. 生成与批准

按文档契约生成 Change；已有等价计划直接引用，不另建 proposal、任务副本或日志文档。无长期文档时只补本次涉及的最小现行基线，区分观察到的事实和待批准的约束。未来能力留在 Change 中，不提前写成当前系统事实。

就绪条件：重要行为和结构约束都有任务及足够的验收方法；必要文档更新有交付责任；依赖正确；要求和检查没有冲突；需要用户决定的事项已经解决。

呈现最终范围、关键设计和验证方法，取得实施批准后才记录 approved。确认拆分不自动批准后来新增的设计。已有明确实施批准且整理忠实保留其范围时记录原批准依据，不再重复索要批准。

输出 Change 路径、批准或未决状态及下一步。规划批准不自动启动 agent-workflow，也不授权发布。用户后续显式请求执行时由 [agent-workflow](../agent-workflow/SKILL.md) 消费这些契约。
