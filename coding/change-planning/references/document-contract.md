# 文档契约

## 文档职责

沿用项目现有位置、审批规则和结构。没有约定时使用以下位置；文档变大后按能力或模块拆分，不提前创建目录体系。

| 文档 | 内容 | 默认位置 |
| --- | --- | --- |
| Spec | 当前有效的行为、约束和重要场景 | `docs/spec.md` |
| Design | 当前模块职责、数据和状态所有权、依赖、接口及关键交互 | `docs/design.md` |
| ADR | 重要决定的理由、替代方案和后果 | `docs/adr/<number>-<decision>.md` |
| Change | 本次行为和设计差异、任务、依赖及验证方法 | `docs/changes/<change>.md` |

长期 Spec、Design 持续维护当前系统；ADR 按真实的重要决定累积，不为凑文件数量创建。原始需求和评审记录保留背景与审批依据。现行需求或人工审核的设计文档可直接承担对应契约职责，不另建 agent 专用副本。

Design 写约束，ADR 保存理由，使用链接关联，不在两处复制推理。Glossary 仅在术语需要统一时建立，不是固定交付物。项目无长期文档时只建立当前工作涉及的最小基线，不尝试补全整个系统。

## 来源与权威

1. 先识别适用项目规则、当前有效的审批材料和契约。文件时间或名字不能单独证明其仍然有效。
2. approved Change 的明确差异在本次范围内代表目标；未修改的既有契约继续生效。冲突或授权不明交用户决定，不由 worker 解释成更容易实现的版本。
3. 未交付的共享目标接口由一个 Change 持有，其他 Change 链接并声明依赖；不提前写进现行 Design。
4. accepted Change 是历史，不覆盖后续现行契约。原审批依据和被替代 ADR 的理由保留，不改写历史。
5. 指针指向相关文件、章节或符号。只读与本次变化有关的材料；摘要不能代替重要原始约束。

## 契约缺口

| 情况 | 处置 |
| --- | --- |
| 已有要求相互冲突 | 引用具体冲突，主 agent 请求用户决定 |
| 缺少影响可观察行为、共享接口、数据语义、持久化或兼容性的决定 | 暂停相关实施，由主 agent 补充契约并请求用户批准 |
| 不改变契约的局部实现选择 | worker 自行决定；有价值时在交接中简述，不新增审批 |

改变已批准的行为、结构约束或验证承诺时，先修订并重新批准受影响内容。只有表述整理、任务进度更新或忠实文档同步，不重复产品审批。

## Change 状态与进度

| 状态 | 含义 | 转入条件 |
| --- | --- | --- |
| draft | 尚未批准当前契约实施 | 新建，或契约发生尚未获准的实质变化 |
| approved | 契约已获准，可在授权范围内实施 | 用户真实批准，主 agent 记录批准依据 |
| accepted | 交付门禁通过，长期文档同步完成 | 必需任务、审查、同步和最终验证完成 |

状态与批准依据仅由主 agent 更新。批准依据用明确用户指令、可恢复会话位置或审批材料指针，不虚构批准记录。文件状态本身不授予委派、发布或超范围操作权限；恢复时核实批准范围和当前材料的一致性。

Change 的任务项是默认进度台账。主 agent 在检查 worker 证据且拥有该工作树写入权时更新进度；worker 返回结果，不修改需求、设计或批准状态。项目另有权威 issue/task 系统时引用它，不重复维护任务状态。

多份 Change 相互依赖时，只有前置交付达到计划约定的可用门禁才推进后续工作，不能仅凭任务勾选。业务独立也不自动允许并行写入。只有数量已难以导航时才建立只含链接和依赖的总索引。

## Change 最小格式

每份 Change 写清目标和非目标、行为差异、必要设计差异、任务及依赖、验收方法，以及来源和长期文档更新位置。格式见 [模板](change-template.md)，只保留有实际内容的部分。

任务用可验证的行为交付表达，带必要的模块或契约定位，不预设大量文件编辑步骤。持久契约用稳定概念；即时 worker 交接可给具体路径和符号。编号仅在交叉引用有帮助时使用，不强制多套编号系统。

检查说明预期结果、会暴露的违约和实际证明范围；写下完整命令或明确的事实核对方法。详细日志、red/green 和审查证据留在运行产物，Change 仅按需保留短指针；产物保留到验收、恢复和交接完成。

## 主 agent 同步规则

1. writer 交出工作树后，核实批准差异确实完成，独立审查和证据满足要求。未交付行为不进入现行文档。
2. 将完成的行为差异同步到 Spec，结构差异同步到 Design，重要决定按 domain-modeling 写入 ADR。只修改受影响部分，沿用人工审核规则；忠实同步不重复审批，新增语义必须重新批准并复审。
3. 多份 Change 触及同一文档时按验收依赖串行同步，重新核对后续 Change 的假设，不能覆盖写入。
4. 检查同步后文档与实现一致，最终机械检查针对该树。纯文档变化重跑受影响文档检查；行为或结构变化同时使相关实现验证和审查失效。
5. 门禁全部通过后才标记 accepted。状态或证据指针的最后回写仍需受影响文档检查；若检查失败，保持 approved 并报告阻塞，不宣称完成。

Change 保留为历史，不默认复制归档或删除。文档随实际变更更新，定期审核用于发现遗漏、冲突和失效指针，没有变化就不为时间戳改写。
